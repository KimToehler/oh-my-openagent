================================================================================
WHY IT IS ENOUGH
================================================================================

The four product gates were reproduced independently, and each is guarded against
passing vacuously:

  - S0 could not pass on a config that was silently ignored: the plugin-loaded control
    fires first, and a completed model turn is required before the gate line is sought.
  - S1 asserts both the insertion count and that the payload's contentLength equals the
    source-derived 276, anchored on the closing brace, so an unrelated injection or a
    prefix-length collision cannot satisfy it.
  - S2 waits for a NEW completed assistant turn past a baseline rather than sleeping,
    so "no re-delivery" is measured after a turn that genuinely occurred.
  - S3 is the one asserting zeros, so it carries its own positive controls in its own
    sandbox: the plugin loaded there, and the mock recorded 2 real requests. The zeros
    therefore mean the gate is off, not that the model was dead.

The bundle grep ran before any live step, so the live run exercised a binary that
provably contains the fix rather than a stale one. The nudge length was derived from
source twice, independently of the prior report.

The single failure is attributed to a specific unrelated session in a different repo,
by direct id lookup and by directory query, with the feature's own isolation check
passing. That is a harness limitation on a busy host, not a defect in the nudge, and
it does not touch any of the four gates.

I did not weaken, edit, or re-run any gate to obtain this result. The script ran
unmodified, once.

WHAT WAS OMITTED
================================================================================

- Server passwords, auth headers, and the Authorization values used against the local
  serve instance are omitted. They were per-run random values (oqa-$RANDOM$RANDOM) for
  a 127.0.0.1 listener and died with the run. No token, credential, or API key appears
  in this file or in f3-rerun/. The mock model needs no real key ("not-needed").
- Full serve logs and the 7.4 MB shared plugin log are not copied. Only the matched
  lines and the counts derived from them are recorded.
- f3-resolved-config.json is opencode's own resolved config as returned by the local
  serve endpoint. It is captured for the record; the script deliberately does not
  assert on it, since that endpoint does not expose the omo plugin config.
- The script's exit-1 path skipped its own final teardown echo. I verified teardown
  directly instead (processes, sandboxes, log inode, git status), recorded above.
- I did not re-run the script a second time after diagnosing the DB guard, since
  re-running would not change the four gate outcomes and would have written over the
  restored prior evidence again.
- I did not fix the DB guard's concurrency weakness or the script's shared-EVID
  hygiene problem. Both are script changes, and the brief forbids modifying the script.
  Recommended follow-ups for whoever owns the script: scope the DB assertion to
  sessions attributable to the run (id or directory) instead of a global count, and
  parameterize EVID per run.
