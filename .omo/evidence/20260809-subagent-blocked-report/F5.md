### 3. Implementation matches what the probe found

The probe did not simply green-light the original design. Attempt 1 closed the gate; attempt 2 reopened it at seam level; the orchestrator then cross-checked with an Oracle trace and adopted AMENDMENT A1, which **inverted the original order**. The shipped code implements A1, not the original todo 3 text:

`tools/report-blocked/tools.ts`:

```ts
task.blockedParkCount = priorParks + 1
task.blockedAt = new Date()
task.blockedReason = blockedReason

await manager.notifyBlockedTask(task.id)
const parked = await manager.cancelTask(task.id, {
  source: "report_blocked",
  reason: blockedReason,
  abortSession: true,
  skipNotification: true,
})
```

Mapping to probe findings:

- Probe (a) + A1 FACT 2 (`manager.ts` `if (!aborted) return false` sits before the wake enqueue): the wake is issued **before** the abort, so an abort failure can no longer swallow it. A1.1 satisfied, including the `skipNotification` flip to `true`.
- Probe (b) swallowed child tool result: the tool's success string is expected to be swallowed, which is harmless precisely because the parent was already told. On the abort-failure branch the session is alive, so the `[ERROR] The parent was notified, but report_blocked failed to park this child` string does reach the child. A1.4 satisfied: `cancelTask`'s boolean only decides the child-facing message, never whether the parent was told.
- Probe (c) `task.error` survives into the body: `background-task-notification-template.ts:123` emits `[BACKGROUND TASK BLOCKED]`, `:133-134` renders `**Blocked:** ${task.blockedReason ?? task.error ...}` plus `buildBlockedAnswerInstruction(task.sessionId)`, which produces a literal `task(task_id="<child ses_ id>", prompt="<your answer>")`. `parent-wake-dedupe.ts:123` and `:138` register the new header.
- Probe (d) no permanent uncancellability: `cancelTask` clears `completingTaskIds` in `finally` (`manager.ts` cancel-path `finally` block), and the early-return guard also clears `blockedNotificationTaskIds`, so a re-park is possible. `report_blocked` bounds re-parks at `MAX_BLOCKED_PARKS = 3` and escalates to `failBlockedTask`.
- A1.3 reservation: `reserveNotificationPreparation` is present on the cancel path (`manager.ts:2580-2582`), released in `finally`. See finding 5 for the caveat.

Nothing in the code contradicts an observed probe result. No convenient assumption was substituted for a measured one.

## Findings

1. **PASS - probe evidence completeness.** All four todo-1 questions are answered, each backed by captured raw output. Attempt 1 carries a valid isolation pair (`1631` / `1631`). The document self-labels its weakest claims instead of overselling them.
2. **PASS - probe ran before production code.** No production commit predates the probe file. See the ordering verdict below for the strength of that claim.
3. **PASS - implementation matches probe findings.** The A1 reordering (wake first, abort second, `skipNotification: true`) is exactly what the probe's FACT 2 hazard demands, and A1.1 / A1.2 / A1.4 are all visible in `tools.ts` and `manager.ts`. The blocked header, the reason passthrough, and the literal `task(task_id=...)` instruction line up with probe answers (a) and (c).
4. **PASS - no probe script survives.** Confirmed across the worktree filesystem, `git ls-files`, all-branch commit history, both wave diffs, the stash list, and every registered worktree. `race-probe.test.ts` and `mut-probe.test.ts` were never committed and are absent from disk.
5. **FINDING (medium, consistency) - the A1.3 reservation is not exercised on the production blocked-park path.** `cancelTask` computes `notificationParentSessionID = options?.skipNotification ? undefined : task.parentSessionId` and only reserves when it is defined. `report_blocked` passes `skipNotification: true`, so the reservation added by todo 6 never runs on the real park. The poller window A1.3 targets is instead closed by A1.1's ordering, since the pending wake is queued before the task goes terminal, which is defensible. But the pinning test `blocked-notify.test.ts` "#then notification preparation covers the terminal-to-wake window" calls `cancelTask(task.id, { abortSession: false, reason })` with the default `skipNotification: false`, so it pins a path production does not take. The guard is real but its regression test does not cover the shipped call shape.
6. **FINDING (medium, gate strength) - the gate is closed at SEAM level only, and the harness-level closure it delegated never happened.** AMENDMENT A1 states plainly: "the Todo 1 verdict is SEAM level, not harness level ... F3 MUST close this with a real-harness run ... If F3 shows the parent wake does not survive a real self-abort even with A1.1 ordering, the park step must be redesigned to not abort the child session at all." `F3.md` records **BLOCKED**: `PARENT_RUN_EXIT=1`, `ProviderAuthError`, no child spawned, no BLOCKED wake observed, no resume. The residual risk the probe explicitly deferred is therefore still open at the end of the plan. This is not a probe-integrity defect - the probe was honest about its own level - but the feature currently rests on a seam-level proof plus a defensive reordering, and no run has ever observed a real OpenCode child self-abort delivering the wake.
7. **FINDING (low, derived from probe answer (d)) - abort-failure park leaves a running child that expiry later marks terminal without aborting it.** Probe (d) established that a failed abort returns `false` and leaves the task `running`. In that state `report_blocked` has already set `blockedAt` and armed escalation via `notifyBlockedTask`. `expireBlockedTask` then clears the blocked fields, sets `status = "cancelled"`, and schedules removal, but never retries the session abort. The consequence is a live child session detached from a task record marked cancelled. The implementation is consistent with what the probe observed; the gap is in what happens afterwards. Out of F5's remit to fix, recorded for the owner.
8. **FINDING (informational, hygiene) - the probe's teardown receipt overstates cleanup.** The evidence says "captured `/tmp` artifacts were deleted after extracting above raw output", but `/tmp/omo-self-abort-persistent2/` still holds 18 files (`events.sse` 82 KB, `fake.log` 482 KB, `opencode.log`, `sandbox.txt`, host count files). No probe **script** is among them, so finding 4 stands unaffected. `sandbox.txt` may contain sandbox paths; it is outside the repo and outside the diff, but the claim of deletion is inaccurate.

**INFERRED, with strong corroboration. Not cryptographically proven.**

The plan's own acceptance criterion asks that `git log` show the probe evidence "committed or recorded before the first production commit". The evidence was never committed, and cannot be: `.gitignore:2` (`.omo/*`) excludes it, confirmed by `git check-ignore -v`. So no commit hash attests to it.

What is available:

- Filesystem birth time 17:15:21 and mtime 17:20:37 on `task-1-probe.md`, against committer time 17:28:22 on the first production commit `a7630caaa`. Both git timestamps and file mtimes are user-writable, so this is evidence, not proof.
- `git reflog` independently places `6417390ed` at 14:58:23 and the wave-1 merge at 21:26:00, bracketing the window consistently.
- The strongest link is semantic rather than temporal: AMENDMENT A1 quotes the probe's verdict ("LEVEL: SEAM, all four questions YES") and the wave-1 code implements A1's inverted ordering. The implementation could not have been derived from a probe that had not yet produced that verdict.

Verdict on ordering: every available signal agrees, three of them independent, and no signal contradicts. Treat it as inferred to a high confidence, not as proven.
