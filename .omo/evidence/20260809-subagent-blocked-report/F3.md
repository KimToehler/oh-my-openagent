# F3 - Real manual QA via a deterministic mock provider

VERDICT: PASS, full flow. On a REAL opencode harness with the real plugin and ZERO credentials:
the child reported blocked, the parent received the `[BACKGROUND TASK BLOCKED]` wake, the parent
answered using the exact `task(task_id=...)` instruction from that wake, and the child resumed
and finished. The final hop, previously recorded as an open gap, is now closed - see "FINAL HOP"
below.

This supersedes two earlier attempts: attempt 1 BLOCKED on a missing API key; attempt 2 BLOCKED
on a WRONG diagnosis (see "Corrected diagnosis" below).

## WHAT WAS BUILT

`.agents/skills/opencode-qa/scripts/lib/mock-model.mjs` - an OpenAI-compatible
`/v1/chat/completions` SSE server, the OpenCode twin of the existing codex-qa mock. Unlike that
one it emits TOOL CALLS, because the flows worth QA-ing only happen when the model asks for a
tool. Turns are scripted JSON with `when` / `unless` / `repeat` matchers.

`.agents/skills/opencode-qa/scripts/mock-model-selftest.mjs` - 16 assertions, all passing.

Two guards in the mock were not designed up front. Both were added after observed failures and
are now pinned by self-test assertions:

1. `unless` - a `repeat: true` tool turn made the real agent loop call `report_blocked` 325
   times before the run was killed, because the model kept re-requesting a tool whose result it
   never acknowledged. `unless` makes a repeating tool turn stand down once its result appears.
2. tool turns require the request to actually offer tools - see the corrected diagnosis.

## CORRECTED DIAGNOSIS (attempt 2 was wrong)

Attempt 2 concluded that opencode "sends NO `tools` key" and that a custom
`@ai-sdk/openai-compatible` provider cannot get tool capability resolved. That conclusion was
WRONG, and it was wrong because of a measurement error: it inspected only the FIRST request in
the mock log with `head -1`.

Reading opencode's own source at the matching version (~/git/opencode, 1.18.15) disproved it:
- `provider.ts:1236` and `:1464` resolve `toolcall: model.tool_call ?? true`. Capability
  DEFAULTS TO TRUE. The config was never the problem.
- `session/prompt.ts:231` is the title generator and deliberately sends `tools: {}`.

So the first request of any session is legitimately toolless. Per-request inspection of the same
log showed `req0: tools=0` (title generation) and `req1: tools=66`, WITH both `task` and
`report_blocked` present. Tool capability had been working the entire time.

The real bug was in the mock: the toolless title request consumed the scripted tool turn, so the
actual turn fell through to text and the flow silently never ran - which reads exactly like a
broken feature. Fixed by skipping tool turns when a request offers no tools.

Lesson recorded because it nearly caused a false "product is broken" verdict: `head -1` on a
multi-request log is not evidence about request N.

## TWO CORRECT-BY-DESIGN BEHAVIORS FOUND WHILE DEBUGGING

Neither is a defect; both cost time and are worth documenting for the next QA run.

1. `report_blocked` is advertised ONLY in the background-subagent prompt (`prompt-builder.ts:17`,
   scoped by commit `15b298d5f`). A top-level session never sees it.
2. A child spawned with `subagent_type: "explore"` gets `explore`'s restricted 12-tool read-only
   set, which excludes `report_blocked`. A child spawned with `category: "quick"` gets 53 tools
   INCLUDING it. Additionally the child must be spawned with `run_in_background: true` - a
   synchronous child correctly hits the guard
   `[ERROR] This is not a background subagent session.`

## WHAT WAS OBSERVED - THE PROOF

Bundle freshness first, since QA against a stale bundle is worthless: `BUILD_EXIT=0`, bundle
contains `report_blocked` x5, `notifyBlockedTask` x2, `resumingBlockedTaskIds` x5, and 0
background-agent sources newer than `dist/index.js`.

Flow: parent session -> mock emits a `task` tool call with `category: "quick"` and
`run_in_background: true` -> child spawns as a real background subagent -> child's request
carries 53 tools including `report_blocked` -> mock emits the `report_blocked` tool call.

Result, captured from BOTH the live SSE stream and the sandbox database (1 occurrence each):

    <system-reminder>
    [BACKGROUND TASK BLOCKED]
    **ID:** `bg_1dd726ac` | session: `ses_0152810bcffe0uypycyab7AspN`
    **Description:** blocked child
    **Blocked:** Reason: I cannot proceed without the deploy target
    Needs from parent: which environment to deploy to
    **Child needs your answer:** Reply with the requested information using this exact invocation:
    `task(task_id="ses_0152810bcffe0uypycyab7AspN", prompt="<your answer>")`
    **CHILD AWAITING RESPONSE:** Answer the child to unblock it.
    </system-reminder>

This is the feature's entire purpose, observed end to end on a real harness: the child reported
blocked, the parent was told, and it was told exactly how to answer.

The child's own `report_blocked` tool part ends `status: "error"`, `error: "Tool execution
aborted"`. That is EXPECTED and is the behavior the todo-1 probe documented: the child session
is aborted as part of parking, which swallows the tool result. It is precisely why AMENDMENT A1
inverted the order so `notifyBlockedTask()` runs BEFORE `cancelTask(..., skipNotification: true)`.
The parent's wake survives the child's abort - now confirmed on a live harness, not just at seam
level.

## FINAL HOP - NOW CLOSED

The blocker was that the id the parent must answer is minted at RUNTIME: the wake says
`task(task_id="<child session>")`, and no static script can know that value. The mock gained a
`capture` mechanism - a turn may lift a regex group out of a request body and later turns
interpolate it via `{{name}}`. Turns whose placeholders are still uncaptured are skipped rather
than sending a literal `{{name}}` downstream.

Two harness bugs were found and fixed while proving this, both worth recording because each
produced a plausible-looking but WRONG result:

1. Over-escaped regex. The live body contains `task_id=\"ses_...\"` with single backslashes;
   the JSON-encoded pattern had doubled them, so it silently matched nothing. Fixed by
   validating the pattern against the real captured body before use.
2. A DECOY id. The first naive regex captured `ses_abc123` - which appears in the AGENT'S OWN
   SYSTEM PROMPT as a documentation example of `task(task_id="ses_abc123", ...)`. The mock
   dutifully answered a session that never existed. Fixed by anchoring the capture to the wake's
   actual instruction sentence ("Reply with the requested information using this exact
   invocation"). This is a good reminder that a regex over a whole request body sees the system
   prompt too.

Proof of the closed chain, all from one run:

    id inside the wake:      ses_015130d2effeIbVafi3jwOXs9F
    id the parent answered:  ses_015130d2effeIbVafi3jwOXs9F   (identical)

    parent's task tool call:
      status: "completed"
      input: { task_id: "ses_015130d2effeIbVafi3jwOXs9F", prompt: "Deploy to staging. ..." }
      output: "Task continued and completed in 1s."

    child session parts, in order, after the answer:
      {"type":"text","text":"Deploy to staging. That is the answer to your question."}
      {"type":"step-start"}
      {"type":"text","text":"acknowledged, continuing"}
      {"reason":"stop","type":"step-finish"}

The child received the parent's answer as a plain user message, produced output, and terminated
with `reason: "stop"`. That is the feature's full contract: the parent is told, the parent
decides, the answer arrives as a plain message, the child continues.
