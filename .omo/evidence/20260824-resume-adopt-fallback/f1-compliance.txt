NOTE 1 - `absent` liveness policy deviates from the plan text, deliberately,
  but the plan file was never updated to say so.
  Plan .omo/plans/resume-adopt-fallback.md:78 still reads "adopt ONLY on
  `terminal`. Treat `active`, `unknown`, AND `absent` as refusal." The shipped
  code at manager.ts:1405-1410 adopts an `absent` session when
  validateSessionHasOutput (manager.ts:2444) confirms real transcript output,
  refusing only when there is no output. This is a justified correction, not
  drift: a real `opencode serve` omits idle sessions from session.status(), so
  a genuinely idle orphan reports `absent`, and the plan's rule would have made
  the dominant real-world case permanently unresumable. It is recorded as
  "CORRECTION 2 (spec contradiction resolved by user decision)" in
  task-1-red-green.txt:268-298 and documented in the shipped findings entry.
  One pre-existing new-in-this-work test was replaced as part of that policy
  change (the status-registry-unavailable refusal test, added earlier in the
  same work at 2934be9e0, superseded at c40e4fa26); no test that predates this
  work was touched, so MNH8 is not violated. Residual: the plan file on disk
  now contradicts the shipped code and the Must-have MH1 wording, which will
  mislead anyone reading the plan later. Suggest a one-line plan amendment.
NOTE 2 - Local lane branches were created despite "NO new branch".
  git branch shows wt/resume-adopt-lane-1, -2, -3 and wt/resume-adopt-attempt3,
  merged into dev via 06a9ae151, 9f78c5347, 91c367080. The user-facing intent
  of that guardrail (no PR, nothing pushed, work lands on local dev) is met:
  nothing is on origin and no PR exists. The branches were the mechanism for
  the plan's own parallel Wave 1, and the root AGENTS.md worktree mandate
  points the same way. Recording it because the plan's literal wording was not
  followed.
NOTE 3 - Live QA covers the HAPPY path only.
  57-scenarios.txt: HAPPY=PASS (pre=2 post=4), REFUSAL=NOT-REACHED,
  ABSENT=NOT-REACHED. Both unproven paths are covered by unit tests in
  manager.resume-adopt.test.ts and the gap is disclosed in the findings entry
  and the evidence README. Pre-accepted by the audit brief; recorded, not
  counted against the verdict.
NOTE 4 - `manager.findBySession?.()` optional call at
  background-continuation.ts:28. I agree with the decision. ExecutorContext
  declares `manager: BackgroundManager` (executor-types.ts:7), a concrete class
  that always defines findBySession, so in production the optional call can
  never short-circuit and behavior is exactly the intended pre-resume
  observation. It only tolerates incomplete legacy test stubs. Rationale is
  recorded at task-2-red-green.txt:141-143. Does not break production behavior.
  Minor cost: an incomplete stub is silently treated as adopted, which could
  mask a future test regression.
