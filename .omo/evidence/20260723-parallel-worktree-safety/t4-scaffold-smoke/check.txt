ROOT CAUSE (diagnosed, not a defect in the produced skill files):
The literal sed command is line-oriented. Per documented GNU/BSD sed semantics, when a
two-address range's END pattern is a regex, the search for the end match starts on the LINE
AFTER the one that matched the START pattern - even if that same starting line also contains
the end pattern. Empirically confirmed:
  $ printf 'line1\nline2 <!-- ABD:begin x -->INSERTED<!-- ABD:end x --> tail\nline3\n' \
      | sed '/ABD:begin/,/ABD:end/d'
  line1
(lines 2 AND 3 both vanish, even though the ABD span was fully closed on line 2 alone.)

Two things compound this for our real files:
1. Every one of this task's spec-mandated edits (2a, 2b) is an INLINE substring insertion -
   `<!-- ABD:begin ... -->...<!-- ABD:end ... -->` sit on the SAME line as the surrounding
   prose (this is the exact literal text spec SECTION 2a/2b prescribe - reproduced verbatim,
   not paraphrased). Because start+end never "self-close" per the sed rule above, the range
   opens at the FIRST such line and does not close until the NEXT line (searched from the
   line after) that happens to contain the literal substring "ABD:end" - which, for a file
   with multiple such inline edits, is some other, unrelated edit's line, deleting every line
   in between.
2. The mandatory FORK-ADAPTATION header (spec SECTION 3, reproduced verbatim) itself contains
   the literal example text "<!-- ABD:begin ... --> / <!-- ABD:end ... -->" inside its
   "resync:" explanation line. That literal example text matches /ABD:begin/ and opens the
   ABD-delete range from INSIDE the header itself, before the header's own closing "-->" is
   even reached by the FORK-ADAPTATION command - and that range then only closes at the
   file's next real ABD-marked edit (the Stop-rules line), deleting the entire body in
   between. This is why the diff shows the whole file body as "missing."

This is a mechanical limitation of the specified sed one-liner on same-line marker pairs, not
a verbatim-fidelity problem with the produced files. A corrected, non-greedy DOTALL strip
(python re.sub, matching each ABD span and the FORK-ADAPTATION block as a real bounded region
rather than a line range) proves the base bodies ARE byte-identical to upstream outside the
ABD-wrapped/header spans:

$ python3 -c "
import re
for f in ['SKILL.md', 'references/full-workflow.md']:
    s = open(f'/Users/tim/.config/opencode/skills/ulw-plan/{f}').read()
    s2 = re.sub(r'<!-- FORK-ADAPTATION.*?-->\n', '', s, count=1, flags=re.DOTALL)
    s2 = re.sub(r'\s?<!-- ABD:begin.*?-->.*?<!-- ABD:end[^>]*-->', '', s2, flags=re.DOTALL)
    shipped = open(f'/Users/tim/git/oh-my-openagent/packages/shared-skills/skills/ulw-plan/{f}').read()
    print(f, 'MATCH' if s2 == shipped else 'DIFFER')
"
