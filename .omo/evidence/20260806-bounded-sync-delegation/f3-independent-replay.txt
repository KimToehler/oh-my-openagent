1. HARNESS AUDIT - is the prior lane's harness rigging the result?
================================================================================
Both prior-lane files were read in full before anything was executed:
  .omo/evidence/20260806-bounded-sync-delegation/task-11-run-qa.sh
  .omo/evidence/20260806-bounded-sync-delegation/task-11-fake-llm-busy.mjs

FINDING: NO RIGGING FOUND. Specifically checked and cleared:
  - The harness NEVER writes, greps for, or injects a `bg_` string. The handle
    is only ever read back out of the tool output.
  - The `bg_` id is generated in product code, not in the harness:
      packages/omo-opencode/src/features/background-agent/manager.ts:666
        id: `bg_${crypto.randomUUID().slice(0, 8)}`
    Proof it is not a fixed/injected constant: the prior lane recorded
    bg_75870ee5; my independent bounded run produced bg_74edac0b. A different
    random id on each run is exactly what randomUUID predicts and what an
    injected constant could not produce.
  - The "busy child" is genuinely busy: the fake provider answers the child
    session with a real `bash sleep N` tool call, so the busy-ness is opencode
    executing a real subprocess, not a status string the harness asserts on.
  - The bounded vs control switch is a single config key. The harness does not
    branch on it anywhere else.

I nonetheless wrote my OWN driver and my OWN fake provider rather than reusing
theirs, so no prior-lane artifact could carry over:
  /tmp/omo-f3/f3-run.sh
  /tmp/omo-f3/fake-llm-f3.mjs
My version adds one thing the prior lane lacked: the child's bash command
appends TIMESTAMPED BEATS TO ITS OWN FILE
  echo "$(date -u +%s) F3_CHILD_BEAT_START_<n>" >> child-beats.txt
  sleep 6
  echo "$(date -u +%s) F3_CHILD_BEAT_END_<n>"   >> child-beats.txt
and the PARENT writes a DIFFERENT marker to a DIFFERENT file
(F3_PARENT_HOLD_START/DONE -> parent-beats.txt). This makes child liveness
provable from an artifact that neither the plugin nor the harness authors -
the child's own shell writes it - and makes it impossible to mistake parent
activity for child activity.

CAVEAT ON MY OWN HARNESS (self-reported): I used `date -u +%s%3N`, which is a
GNU extension BSD `date` does not implement, so beat lines read like
"17860224233N" = 10-digit epoch SECONDS followed by a literal "3N". This cost
no evidence: the seconds prefix is a valid timestamp and all comparisons below
were redone at SECOND granularity. Reported rather than silently corrected.
