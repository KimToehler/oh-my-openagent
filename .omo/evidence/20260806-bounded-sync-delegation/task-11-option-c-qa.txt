0. THE QA DESIGN PROBLEM AND HOW IT WAS SOLVED
================================================================================

The bundled fake provider (.agents/skills/opencode-qa/scripts/lib/fake-openai-server.mjs)
answers a child session in ONE turn, in well under a second. A child like that
goes idle immediately, so a 60s wall-clock bound could never trip and the
"bounded" run would be byte-identical to the "unbounded" run - which the task's
gate F3 declares an automatic FAIL.

So a new fake provider was written that makes the child STAY BUSY:

  .omo/evidence/20260806-bounded-sync-delegation/task-11-fake-llm-busy.mjs
  (source of truth during the run: /tmp/omo-qa-t11/fake-llm-busy.mjs)

  - It reuses the bundled `sendSse` / `textEvents` / `toolCallEvents` SSE
    encoders verbatim (imported from the skill's fake-openai-events.mjs), so the
    wire format is the same one the skill's own scripts already validate.
  - The CHILD branch answers every child request with another
    `bash: sleep 6; echo CHILD_ALIVE_TURN_<n>` tool call, 20 times
    (CHILD_TURNS=20, CHILD_SLEEP_S=6). The child therefore holds a continuous
    busy/running status for roughly 127 seconds - more than twice the 60s bound.
  - This is also the HONEST test. A child that is continuously active is exactly
    the case the pre-existing INACTIVITY window (syncPollTimeoutMs /
    MAX_POLL_TIME_MS) can never catch, because every busy tick resets it. That
    is the entire reason the wall-clock ceiling exists.
  - The PARENT branch, after its `task` tool call returns, issues one long
    `bash sleep 100` to hold the parent turn open. Without it, `opencode run`
    tears the server down the instant the parent turn ends and there is no
    observable window in which to prove the child survived. (First bounded run,
    label "bounded", was run WITHOUT this hold and demonstrated the problem:
    the yield fired correctly but the process exited too fast to sample child
    liveness afterwards. That run is retained at /tmp/omo-qa-t11/out/bounded.)

Provider self-test before use (literal output):

  $ curl -s -X POST "http://127.0.0.1:$PORT/v1/responses" -d '{"input":[{"role":"user","content":"Run the wallclock probe"}]}'
  data: {"type":"response.output_item.added",...,"name":"task",...}

  -> parent asks for a SYNC delegation (run_in_background:false); child answers

IMPORTANT PRECISION - what "unset" actually means at runtime. The task brief
said an unset key defaults to Infinity. That is true of the TIMING SYMBOL
(timing.ts: `let MAX_WALL_CLOCK_MS = Infinity`), which is the inert default so
the feature cannot change behavior unless configured. But the PLUGIN WIRING
supplies its own default when the config key is absent:

  packages/omo-opencode/src/plugin/tool-registry-core-tools.ts:68
    syncWallClockTimeoutMs: pluginConfig.background_task?.syncWallClockTimeoutMs ?? 600_000,

So an unset key yields a 600000 ms (10 minute) ceiling in a real plugin session,
not Infinity. This does not weaken the control: the child's total runtime is
~127 s, an order of magnitude below 600 s, so the ceiling is never reached and
the run behaves exactly as an unbounded sync wait. The control is honest about
what it demonstrates - that WITHOUT the configured 60 s bound the parent blocks
for the child's full duration and gets a result rather than a handle.
