4. VERDICT: GREEN - THE CEILING INVARIANT SURVIVED THE FIX UNCHANGED
--------------------------------------------------------------------
Why the 300_000 ms retained-admit ceiling was unaffected on the paths this test
exercises:

lastAdmitOnlyDepositAt is written in exactly one place, markRetainedNoReplyAdmission
in parent-wake-prompt-dispatch.ts line 175, and only after the guard at lines
164-166 confirms the dispatch was an admit-only deposit (retainPendingWake true
and forceNoReply true). In this test that write happens once, at the t = 100_000 ms
admit-only deposit, so the ceiling clock in shouldAdmitRetainedWakeAfterCeiling
starts there and reads 120_000 ms elapsed at the second flush, far below the
300_000 ms threshold. The new coalesce branch added by 5113f9124 sits at
parent-wake-prompt-dispatch.ts line 118 and is guarded by
`isDiscardedCoalesceDispatchResult(promptResult) && !isAdmitOnlyDispatch(input)`,
so it is structurally excluded from admit-only deposits and cannot requeue or
re-time them. It also requires a discarded-coalesce dispatch result, which the
test's stubbed promptAsync (a plain resolved `{ data: {} }`) never produces, so
the branch is not reached at all in these six cases. The behavior change the task
description anticipated, the ceiling now measuring from the last REAL deposit
instead of being pushed forward by phantom deposits, is real in production but
does not manifest here because this test never generates a phantom deposit in the
first place.

Note on honesty: the above is derived from reading the guards and the stubbed
client in the test, plus the observed pass result. I did not instrument the run
to print lastAdmitOnlyDepositAt at each step, so the mechanism is established by
code path analysis rather than by a runtime trace of that field.
